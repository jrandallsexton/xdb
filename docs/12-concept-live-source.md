# 12 - Concept: XDB over a Live Source Database (Two-Way)

Status: **thinking aloud, for discussion** (2026-10-23). Nothing decided; not planned. Related: `09-concept-sportdeets-overlay.md` (one-way export/import).

## 1. The question

`09` moves data one way: the source exports a bundle, XDB imports it. What if XDB were also allowed to **write back** to the source, so it is not a one-time export but a live tool over an ordinary relational schema? Can a normal schema fit XDB's object model at all?

## 2. Background: EAV

XDB stores data as **EAV (Entity-Attribute-Value)**. Instead of one table per kind of thing with one column per field, everything lives in a few generic tables:

| EAV part | In XDB | Example |
|---|---|---|
| Entity | a row in `Assets` | the asset "Ohio State 2024" |
| Attribute | a row in `Properties` | the property "Wins" |
| Value | a row in `PropertyValues` (asset id, property id, value) | `(Ohio State 2024, Wins, "14")` |

A normal schema has a `FranchiseSeason` table with a `Wins` column; XDB has one `PropertyValues` row per field per asset.

- **Why:** new types and properties are metadata rows, so users define them at runtime with no schema change; per-value history and approval (submittals) come naturally.
- **Cost:** querying EAV is awkward and slow, so XDB compiles its metadata into generated tables and report views that flatten it back into ordinary columns for reading.

## 3. Three ways to relate XDB to a live relational source

| # | Model | How it works | Assessment |
|---|---|---|---|
| 1 | **Copy + two-way sync** | Data is copied into XDB's EAV store; changes are captured and replayed in both directions | Hardest: conflict resolution, two sources of truth, schema drift. Not recommended. |
| 2 | **Mapped types (no copy)** | An asset type is *backed by a table*: properties map to columns, references to foreign keys, Definition/Instance to a foreign key (e.g. `FranchiseSeason.FranchiseId -> Franchise`). XDB already compiles SQL from metadata; it would target the real tables instead of its generated ones. Views, reports, filters and the relationship graph keep working. Writes become generated `INSERT`/`UPDATE` statements, or calls to the source's API. | No copy, no sync; the source stays the single truth |
| 3 | **Hybrid (2 + side-car EAV)** | Mapped columns for what the source owns, plus XDB's EAV for what users add on top (tags, notes, extra properties), keyed by the source row's id | Most flexible; current leaning |

## 4. What gets hard (models 2 and 3)

- **History and approval.** XDB versions every value through submittals; source tables usually do not. XDB would keep its own change journal and apply a change to the source when it is approved.
- **Business rules.** A source's rules often live in its services, not in its schema; writing to its tables directly bypasses them.
- **Type hierarchies.** Parent types (Person -> Athlete, Coach) become UNION views across several tables.
- **Identity.** XDB assumes GUID ids. sportDeets uses GUIDs, which helps; many schemas use integer or composite keys and would need a mapping.
- **Schema change.** The mapping metadata must follow the source's migrations (columns added, renamed, removed).

## 5. sportDeets specifically

Producer owns its writes, and nothing else touches its database (the same rule that makes `09` export-based). Any write-back from XDB would have to go through Producer's API or commands, never direct SQL. Reads could still be direct where a copy of the database is available, or through the API.

## 6. Current leaning

Model 3, with model 2's reads going straight to the source. That turns XDB from a **store** into a **metadata-driven lens over existing data** - arguably a stronger product than the EAV store itself.

## 7. Open questions

1. Is the use case mainly read and explore with occasional edits, or real data entry against the source?
2. Writes through the source's API only, or direct SQL for sources that allow it?
3. Does the submittal and approval workflow apply to mapped types, and where is that journal kept?
4. Can mapping metadata be generated by introspecting a schema (tables, columns, foreign keys), then edited by hand?
5. How does this coexist with the import path in `09` - one engine with two kinds of backing (EAV-stored and table-mapped)?
